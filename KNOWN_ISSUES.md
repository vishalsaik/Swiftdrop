# Known issues and deferred work

Things we decided **not** to build yet, written down so they are not forgotten. The payment rows below are the ones that would hurt in production. Each has a "when" so we know what unlocks it.

## v1: what it is not

v1 is the whole journey working end to end (see the README). This is what it leaves out on purpose, and what that costs.

- **Drivers are a stand-in.** `/accept` assigns a random id; there is no driver registry, no driver app, no dispatch and no location. The order's driver is not shown by name anywhere.
- **Nothing is sent to a customer.** No email, SMS or push. The customer sees status on the dashboard; the messages the dispatcher sees are a preview of what a customer app would say.
- **Accounts have no email.** A forgotten password is reset by a staff member, who passes the temporary password on by hand. There is no self-service reset, no email checking and no two-factor sign-in (see Orders and API).
- **Menus are plain.** A name, a description, a price in dollars (one currency, fixed) and sold out or not. No categories, photos, options or sizes, opening hours, stock counts, tax, delivery fee, tips or discounts. Items and restaurants cannot be deleted (an item is marked sold out, a restaurant is closed); a staff member can change any restaurant's menu, there is no per-restaurant login.
- **Closing a restaurant or selling out an item affects new orders only.** Orders already placed carry on, and an item that sells out between a customer opening the order sheet and pressing Place order is refused with a message naming it (the customer picks again).
- **The order drawer shows the restaurant's id, not its name.** The order keeps the name and price of each line, not the restaurant's name.
- **The Docker stack is for trying it and for a small deployment, not a hardened one.** The database password in `docker-compose.yml` is a default (the database is not published, so only the containers can reach it, but change it for anything real); there is no TLS (put a proxy in front and set `COOKIE_SECURE=true`); no backups; one server. The schema is one idempotent file, applied by `cmd/migrate` (an upgrade is applied in place, there is no "down" and no record of which version a database is at).
- **The CI workflow has been verified in pieces, not run by GitHub.** Every step was run locally (gofmt, vet, the race-detector tests against Postgres, the dashboard's checks, the stale-build check in a clean Linux container, the Compose stack and the end-to-end test against it). The first run on GitHub may still find a difference such as a tool version.
- **The dashboard shows what a customer would, to a customer too**, but it was designed for dispatch first: there is no separate customer app.

## Finding food near you

Built: restaurant places, a delivery radius, vegetarian items, and `GET /search` (README, "Finding food near you"). What it leaves open:

- **Distance is in a straight line, not by road.** A restaurant 2 km away across a river may be a 15-minute ride. The delivery radius is a circle for the same reason.
- **Typed addresses and delivery addresses are built** (see "Delivery addresses and address search" below), so a customer who refuses location can search for an address, and every order is checked against the restaurant's radius.
- **Places are typed in by staff.** There is no menu or restaurant import yet, so a new restaurant has no place until someone enters its latitude and longitude (or stands in it and presses "Use my current location"). A restaurant that is not placed is found by name but never by a search that has a position, and (since delivery addresses) it takes no delivery orders at all.
- **The position is looked up once, not followed.** A customer who moves presses the button again. Following a moving person or driver on a map belongs with the driver work.
- **The position is in the address of the request** (`/search?lat=...&lng=...`), rounded to about 110 metres first. Server logs that record addresses would hold that rounded position; the server itself logs no request addresses and keeps nothing.
- **Search is simple.** Words are matched as substrings, and an item's own name also by trigram similarity (so "pad thay" finds "Pad thai"). There is no stemming, synonyms ("fries" and "chips"), spelling correction of restaurant names or descriptions, other languages, or ranking by popularity or rating. Postgres is fast enough for tens of thousands of items; a search engine (Meilisearch or Typesense) behind the same route is the next step, and instant as-you-type results would need it.
- **Location needs `https://`.** Browsers only offer it on secure pages (and `localhost`), so the Docker stack on plain HTTP works on the same computer but not from a phone on the network until TLS is in front of it.
- **The search answers are not cached and not paged.** At most 30 restaurants with 8 items each.
- **The demo seed's places are real (Indiranagar in Bengaluru, Bandra in Mumbai) but the restaurants are not.** Running `seed` on a database seeded before places existed places the demo restaurants that have no place yet, and changes nothing else; items seeded earlier keep their old vegetarian flag (not vegetarian) until staff mark them.

## Delivery addresses and address search

Built: saved addresses, an address search, "where I am", and a delivery check on every order (README, "Where an order goes"). What it leaves open:

- **The coordinates come from the client.** A customer could send an address whose words say one place and whose coordinates say another, to pass the radius check. The cost falls on them (a driver cannot find the door, the order is cancelled and refunded), not on us, and customers legitimately adjust a point, so the server does not sign what the search returned. If delivery fraud becomes real, sign the candidates and refuse coordinates the search did not give.
- **No map and no pin to drag.** The customer confirms an address as text. How close the point is to the door depends on the geocoder: OpenStreetMap is good for streets and areas in many cities and often lacks house numbers, so the landmark field matters.
- **The public Nominatim is not for traffic.** Its policy allows about one request a second for the whole service, and our limit is 30 a minute per person, so many people at once would exceed it. The answers are cached for an hour in memory (a restart empties it, and several servers each ask for themselves). Run your own Nominatim, or a service that speaks its protocol, before real use.
- **What is typed in the address search goes to a third party,** the geocoder, and the dashboard says so. The server sends nothing else about the person.
- **A paid geocoder may not allow what we do.** Google and Mapbox restrict storing the coordinates they return (we keep saved addresses and each order's copy); Nominatim-compatible services built on OpenStreetMap data do not, but need the "© OpenStreetMap contributors" credit, which the dashboard shows. Check a service's terms before pointing `GEOCODER_URL` at it.
- **The delivery check is a circle.** Straight-line distance within the restaurant's radius; no delivery zones drawn on a map, no delivery fee by distance, no estimated time.
- **Addresses are personal data.** A person can remove each saved address, but accounts cannot be deleted yet, so what they keep stays until they remove it, and an order keeps its copy of the address for as long as the order exists. There is no export.
- **No contact number.** A driver (when there are drivers) cannot call the customer: no phone number is collected.
- **Old orders have no address,** and an address cannot be added to an order after it is placed.
- **Staff placing an order for a customer cannot use that customer's saved addresses** (they are the customer's own); staff search for, or type in, the address. With no geocoder set up, staff type the street and its coordinates by hand.
- **Saved addresses have a label but no "default".** The customer chooses each time.
- **The demo geocoder knows eight streets** (Indiranagar and Bandra), enough to try the product and to test it, and nothing else.

## Payments: production issues we are accepting for now

| # | Issue | What happens | Why we accept it for now | Unlocked by |
|---|-------|--------------|--------------------------|-------------|
| 1 | **A payment can still wait for a person** | No webhook event ever arrives and nobody retries: the request never reached Stripe (no money moved), or Stripe's event was lost (our endpoint was down, or had no secret, for longer than Stripe retries: about 3 days in live mode). Mostly fixed: the reconciler asks the provider what became of it (never charging again), records a success or a refusal, abandons an attempt the provider has no record of after 30 minutes, and after 20 hours of no answer (the provider cannot be asked, or never decides) hands it to a person: `needs_review`, an alert, no new attempt for the order. What is left is that person: nothing notifies them (see 6), and until they act the order stays `payment_pending`. | Retrying is the **user's** decision, and no code path may re-send a charge on its own (that could charge someone who walked away). | A notification channel, and a screen to settle a payment by hand |
| 2 | **Money may still have moved with no record** | The provider charged, but the response was lost or `FinishPayment` failed. The webhook records this when Stripe's event arrives (seconds later, retried for about 3 days). It stays unrecorded only if that event is lost or `STRIPE_WEBHOOK_SECRET` is not set, and then it looks identical to "never reached the provider". | We cannot tell the two apart without asking the provider. | Provider lookup |
| 3 | **A retry more than ~24 hours later is a new charge** | Fixed. Stripe prunes idempotency keys after at least 24 hours, so re-sending the same key would be a new charge. A retry of a payment older than 20 hours is no longer sent: it is marked `needs_review`, an alert is raised and the retry is answered `409`. The age is read from the application clock, which only matters to the minute, not to the second. | | |
| 4 | **A customer can pay twice through a new order** | The old order errors, the customer places a new one and pays again. If the first charge succeeded, they paid twice. The webhook and the reconciler shrink this to the time before one of them settles the old payment (about two minutes at best: the reconciler leaves a payment alone for 2 minutes), after which the old order is visibly paid. | Nothing links the two orders, and cancelling the duplicate is a person's call. | Matching orders by customer, then a refund tool |
| 5 | **Charged but cancelled** | Fixed. The provider's answer is kept even when it arrives after the cancel (an authorized payment on a cancelled order), and the refund job gives the money back within one interval (30 s by default). A refund that fails 5 times is marked `failed` and raised as an alert for a person, and so is one Stripe accepts and reverses later (`refund.failed`). What is left is the person (see 10). | | |
| 6 | **Alerts reach a chat channel, and nothing else** | Mostly fixed: with `ALERT_WEBHOOK_URL` set, each alert is posted to a webhook (Slack-compatible), retried, and repeated as a reminder while it stays open. What is still missing: email, a pager, and a metric on open alerts. With no webhook set, an alert still waits for someone to open the dashboard. The message format is Slack's `text` field plus structured fields; it was tested against a local server, not against a real Slack or Discord channel. Delivery is at least once (a duplicate is possible), a channel that is down is retried forever while the alert is open, and a reminder is the only way to hear about an alert twice. | One channel is enough until there is an on-call rota. | A pager sink, and a metric on open alerts |
| 7 | **A charge found after we gave up is only an alert** | The reconciler abandons an attempt the provider has no record of after 30 minutes, then never looks at it again. If the provider reports a charge for it later (a very slow search index, an unusual outage), only the webhook can say so, as a `contradicting_event` alert. Without `STRIPE_WEBHOOK_SECRET` nobody notices. | The 30 minutes is long against Stripe's list API, which is current. | Re-checking abandoned payments for a day |
| 8 | **Payments claimed before the charge carried metadata cannot be found** | The lookup finds a payment by the `metadata[payment_id]` the charge sends. A payment claimed by an older build has none, so a lookup says "no record" and the attempt is abandoned after 30 minutes even if it was charged. | There is no real traffic yet. Before running this against a database with live `processing` payments, settle them by hand. | |
| 9 | **The Stripe lookup lists recent payment intents** | It reads every intent created since the claim (up to 2,000) and picks ours, because Stripe's search is eventually consistent and not offered to every account. Past 2,000 it gives up with an error, never "no record", and the payment goes to a person after 20 hours. | Fine at this volume. | Stripe search, or storing the intent id before confirming |
| 10 | **A failed refund needs a person, but they can say it is done** | Mostly fixed. When Stripe reverses a refund, or the job gives up, the refund is `failed` and an alert asks a person to refund the customer. Nothing refunds again on its own (a second refund could pay out twice). Once the person has done it they record it (`POST /orders/{id}/refund`, or the dashboard): the refund becomes `refunded`, the ledger says it was done by hand and by whom, the alerts close and the customer is told it was sent. What is still open: the reference is **not checked with the provider** (the person is trusted, and the ledger shows who), a recording **cannot be undone** (only a provider reversal of that refund id sets it failed again), a refund can only be recorded **in full** (no partial amounts), and nothing yet lets a person record a refund for a payment whose refund is `refunding` and stuck. | A person is trusted to say it is done; there is no real traffic yet. | Checking the refund with the provider, and partial refunds |

## Payments: design not built

- **The ledger is a history, not yet a double-entry book.** `payment_events` records what happened to each payment, written by the database itself and append-only. It does not hold amounts as debits and credits, so it cannot yet be reconciled against Stripe's settlement reports. **Do not delete payment rows**: a row holds the `provider_payment_id` a refund needs, and a payment with a history cannot be deleted anyway.
- **No provider lookup, metadata or create-the-PaymentIntent-first.** Ignored on purpose until the ledger exists. Today the gateway creates and confirms in one call and sends no metadata. The webhook matches events through `event.request.idempotency_key` instead, so an event that none of our requests caused (a dashboard refund, a dispute) carries no key and is ignored.
- **No auth-then-capture, no end-of-day reconciliation, no polling reconciler.** Real payment systems layer these under webhooks as backstops. Not planned yet.
- **Refunds are automatic but basic.** One full refund per payment, made by a job inside the API process (`REFUND_INTERVAL`). No partial refunds and no refund reasons. A separate `cmd/worker` process would be the next step, since jobs should not share a process with request handling.
- **Client `Idempotency-Key` header is ignored.** Our own payment uuid is the key.
- **A retry or takeover must send the same body.** Otherwise Stripe reports an idempotency conflict.

## Payments: the webhook

Built: `POST /webhooks/stripe` (see the README). What it leaves open:

- **Checked against real Stripe test mode (2026-11-01)**, with real charges through our own server and `stripe listen`: a charge with our exact request is accepted and a card success and a decline are each read correctly; `payment_intent.succeeded` and `payment_intent.payment_failed` both arrive with `request.idempotency_key` equal to our payment id, are signature-verified and matched (so the lost-reply recovery rests on something real); `refund.updated` does fire for an ordinary refund (status `succeeded`) and is read and ignored as not a failure; the reconciler's lookup finds a charge by the `metadata[payment_id]` we send and settles the payment and its order (tried by putting a real charge back into the "reply lost" state); a cancelled paid order is refunded through Stripe by the refund job on the first attempt, with a real `re_` id.
- **Still not checked against real Stripe:** only the exact payload of a refund that fails (`refund.failed`, and whether `refund.updated` also fires with a failed status then), which the CLI cannot generate. We read both and match on the payment intent, which is on every refund event. `stripe trigger` fixtures make requests of their own, so their events carry no key of ours: only real charges through our server prove this. `scripts/stripe-dev.ps1` sets up a matching listener and server.
- **Production setup.** A public HTTPS endpoint and a separate `STRIPE_WEBHOOK_SECRET` for test and live mode. Without the secret the route answers `404`, Stripe's deliveries fail, and after its retry window they stop. Secrets should be rolled periodically; the parser accepts several `v1` signatures while one rolls.
- **Only a few event types are handled**: `payment_intent.succeeded`, `payment_intent.payment_failed` (a definite decline, as in the synchronous path), `refund.failed`, and `refund.updated` when the refund ended up failed or canceled. Stripe's guide does not say whether `refund.updated` also fires when a refund fails (it names `refund.failed` for that), so both are read. Not yet seen from real Stripe: the payload of a refund that actually fails.
- **Events can arrive out of order.** A second event that contradicts a recorded outcome raises a `contradicting_event` alert and changes nothing.
- **No table of processed event ids.** Compare-and-set makes a duplicate harmless today. A table would be needed once a handler has side effects (an email, a refund).
- **The work happens inline.** Stripe wants a quick `2xx`. One transaction is fine; a queue is for when the handler does more.

## Orders and API

- Nothing sweeps old `payment_pending` orders.
- A `payment_pending` order whose payment never gets an answer (the request never reached Stripe, or its event was lost) stays pending until someone cancels it.
- Orders made before menus existed carry the name and price their client sent; orders made since carry the menu's, copied at the time. An order placed by staff for a "walk-in" has a free-text `customerId` that belongs to no account.
- Orders made before accounts existed carry a free-text `customerId` (like `cust-1`) that belongs to no account, so only staff can see them. A customer's own orders are the ones placed after they signed up.
- **Accounts are managed, but not fully.** Staff make accounts, switch them off and on, and reset passwords (dashboard **People**, or `/users`), with a history of who did what. What is still missing: **no email address checking** (an account can be made with any address, and a temporary password has to be passed on by hand, since nothing can send an email), **no self-service reset** (a person who forgot their password asks a staff member), **no two-factor sign-in**, **no deleting** an account (a database change), and **no changing someone's role** (promoting a customer to staff is deliberately not offered: make a new staff account instead). Any staff member can disable or reset any other staff member, so a stolen staff account can lock out the others; the history shows who did it, and the last active staff account is always protected. A temporary password is shown to the staff member who made or reset it, so that person knows it until the account's owner replaces it. `go run ./cmd/user` still makes the first staff account, and its generated password is not marked temporary (it says to change it, but nothing makes you).
- **The sign-in limits live in the server's memory.** Several servers each count for themselves, and a restart forgets the counts. They are per email (5 in 15 minutes), per address (30) and for sign-ups per address (10 an hour).
- **The address that is limited is the connection's, not a forwarding header.** Behind a proxy that is the proxy's address, so every person would share one limit until the server is told which proxy to trust.
- **Sessions use the application's clock.** Their lifetimes are days and hours, so a few seconds of drift between servers does not matter, unlike the payment leases, which use the database's.
- **One CSRF token per session, kept for the session's life.** The cookie is `SameSite=Strict` as well, which already stops other sites from sending it, so the token is the second layer.

## The customer view

- **The cart is held in memory.** It is gone on reload and on signing out, and adding from another restaurant starts a new cart after a warning on the page, not a confirm. Keeping it in the browser per account, the confirm and a cart page with its own checkout are the next roadmap item. Until then **Check out** opens the order sheet filled from the cart, and **Start an order** on the Food home still opens the order sheet empty.
- **A card's distance and "delivers here" are worked out in the browser** from the restaurant's place and radius, with the server's own formula and rule; they are for showing, and the server checks the address again when the order is placed. Straight-line distance, as everywhere (see "Finding food near you").
- **A restaurant page is a view inside the Food tab, not an address of its own:** the browser's Back button does not go back to the cards (the page's own back button and the Food tab do), and a reload returns to the Food home with no address chosen.
- **Restaurant cards have no photos, ratings, opening hours or delivery times,** because restaurants have none yet. A closed restaurant is never listed for a customer (the server hides it); one that closes while its page is open is only noticed when the order is placed.
- **The tracker is the order drawer.** A customer's order opens in the same panel staff use (journey, items, delivery address, pay and cancel), with no payment history. It has no map and no driver, because drivers are still a stand-in.
- **One app, two shells.** A customer and staff run the same bundle and the same API; the role decides the shell. Hiding a staff tool is only a convenience, as it always was: the server answers `403` or `404` for anything a customer may not do, and a test checks that a customer's view never asks for staff-only routes.
- **Sample orders are a staff tool.** A customer with no orders is pointed at Food instead.

## The dashboard

- It polls every 3 seconds. Pushing changes to the screen (server-sent events) is not built.
- Its rules (`logic.js`) and its screens (in a simulated browser, against a fake server) have automated tests. How it looks, the animation and the phone layout were checked by hand in a browser, so a change to those needs a look in a browser.
- The build output in `web/static` is committed, because the Go server embeds it and `go run` must work without Node. After a change in `web/ui`, run `npm run build` there and commit the result; a stale build is the one thing no test can tell, because both halves are valid on their own.
- Two libraries.dev effects are used, both only for the long wait of a payment that has no answer yet: a thinking orb beside such an order, and a border beam round its notice in the inspector (off for people who ask for less motion). Short waits keep plain CSS dots. Both draw every frame, so many orders waiting at once would mean many animations; that is fine while a stuck payment is rare. They added about 110 kB to the script (270 kB to 380 kB, 107 kB gzipped). Bot avatars were not used: a driver is only an id.
- The customer messages are shown to the dispatcher, as a preview of what the customer would see. Nothing is sent to a customer: there is no customer app, email or push yet.
- It uses the system font (SF on Apple devices, Segoe UI on Windows, Roboto elsewhere), so there is nothing to download and it looks different from device to device.
- Shutting down on Ctrl+C (the server stops, then the refund job finishes what it is doing) is in `main.go`, which has no automated test.

## Performance and structure

- The payment cache (`internal/paymentcache`) holds only authorized payments and only serves `/pay`. It is per process, which is fine because what it keeps never changes, and it has no expiry for the same reason (an entry leaves only when the cache is full). Deleting a payment row by hand would leave it in a running server's cache until a restart; nothing deletes payments.
- `/pay` lives in `internal/paying` (a Facade); the handler is thin. The webhook handler and the reconciler still record answers through `internal/settle`, which `/pay` does not use: `/pay` records through its own `finish` and `keep` because it has already claimed the payment itself. Folding the three into one is possible but would change what a failed write does in each.

## Stand-ins

- Wallet payments go to the same Stripe gateway as cards.
- `/accept` assigns a random UUID as the driver. No driver registry, no dispatch.
- Without `STRIPE_KEY` the fake gateway is used. Use only Stripe **test-mode** keys while developing.
